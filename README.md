# Home Assistant — MB35x8 / виробнича плата

Home Assistant для дому, що працює на актуальній виробничій платі **MB35x8**.
Власник ідентифікує фізичну заміну як RK3588; перенесена ОС досі повертає старі
позначення `OK3568-C/RK3568`. Тут лежить конфігурація плати та супровідні
матеріали.

## Що це за система

| | |
|---|---|
| Плата | Актуальна виробнича MB35x8; фізично RK3588 зі слів власника, перенесена ОС повідомляє OK3568-C/RK3568 |
| Hostname / IP | `ok3568` / `192.168.50.141` |
| ОС | **Ubuntu 20.04.6 LTS**, ядро 4.19.206, aarch64, 4 ядра, **1.93 ГБ RAM** (MemTotal 2 019 024 kB, заміряно 22.08.2026; старіші документи помилково писали 3.8 ГБ) |
| Home Assistant | Core **2026.7.4**, Python 3.14.6 у venv |
| Веб-інтерфейс | http://192.168.50.141:8123 |
| Встановлено | `/userdata/hass/venv` → `/home/forlinx/hass-venv`; `/userdata/hass/config` → `config-standalone` |
| Служба | `home-assistant.service`, автозапуск увімкнено |

## Чому Core у venv, а не Docker

Вендорне ядро Forlinx зібране **без підтримки контейнерів**:

```
# CONFIG_OVERLAY_FS is not set
# CONFIG_VETH is not set
# CONFIG_MEMCG is not set
# CONFIG_CGROUP_PIDS is not set
```

У `/lib/modules/4.19.206` лежать усього 3 модулі. `docker.io` встановлюється, але
демон падає на старті — не може створити міст `docker0`, бо модуля `bridge` в ядрі
немає взагалі. Сховища теж немає: без overlayfs лишається тільки `vfs`.

Змінити це можна лише перезбіркою ядра з SDK Forlinx і перепрошивкою, а прошивка
цієї плати має відомий проблемний статус.

> Home Assistant Core у venv є технічно працездатним, але з релізу 2025.12 цей
> спосіб встановлення офіційно не підтримується. Стратегічний напрямок —
> перевірений вендорний образ із новішим ядром і Home Assistant Container або
> перенесення HA на окремий підтримуваний хост.

## Безпечний порядок роботи з конфігурацією

Плата і Git-репозиторій можуть розійтися, якщо Home Assistant UI або інша сесія
змінить YAML між копіюванням і перевіркою. Перед кожною сесією:

1. Звірити SHA-256 файлів у `board-config/` з `/userdata/hass/config/` і live
   unit-файлом `/etc/systemd/system/home-assistant.service`.
2. Перевірити `git status`, поточний commit і час модифікації live-файлів.
3. Перед перезаписом створити датований backup кожного цільового файла.
4. Після копіювання виконати:

   ```bash
   /userdata/hass/venv/bin/hass --script check_config -c /userdata/hass/config
   ```

5. Лише після успішної перевірки перезапускати `home-assistant.service`, а потім
   повторно звірити SHA-256.

Критичні параметри плати: timezone `Europe/Kyiv`; `TimeoutStopSec=120`; секрети,
`.storage`, база даних і журнали ніколи не копіюються в Git.

Swap реалізовано як 1 ГіБ стисненого zram через
`board-config/systemd/zram-swap.service`. Він використовується лише при дефіциті
RAM і не створює постійних записів на eMMC. Старий неактивний `/swapfile` на
4 ГіБ видалено.

Операційний план віддаленого доступу, NAS-копій, журналів і міграції платформи
описаний у `OPERATIONS.md`. Home Assistant пише backup безпосередньо в NFS-папку
NAS через `userdata-hass-config-backups.mount`, а `homemate-nas-sync.*` погодинно
експортує лише journald; секрети NAS у репозиторій не потрапляють.

Контур поливу побудований у два шари: Irrigation Unlimited керує насосом,
клапанами й чергою зон, а Smart Irrigation розраховує потребу у воді за
Open-Meteo, опадами та evapotranspiration. Фізичний автозапуск заблоковано
окремим helper-перемикачем до завершення вимірювання витрати кожної зони.

Насос вмикається завжди й без жодних умов — фізичною кнопкою на модулі,
тумблером в інтерфейсі, будь-як. Робота без відкритого клапана нормальна: на
ділянці є водяні розетки для шланга, і це не аварія. Ручний пуск нічого не
відкриває сам і ніщо його не глушить. Ліміту тривалості теж немає: автоматизація
«максимальна робота насоса» свідомо стоїть на `0 = без ліміту` (назва
`irrigation_pump_max_runtime_3h` історична). Не додавайте логіку, яка вважає
насос без клапана збоєм і не «повертайте» три години: подробиці у
`.claude/skills/home-assistant/references/irrigation.md`.

## Структура репозиторію

| Тека | Вміст |
|---|---|
| `board-config/` | конфігурація Home Assistant з плати: `configuration.yaml`, автоматизації, скрипти, чотири YAML-дашборди |
| `board-config/scripts/` | скрипти плати: журнал сповіщень, показники води, тарифи, глибина статистики, похвилинні зрізи, копія статистики, встановлювачі |
| `board-config/www/` | дев'ять власних Lovelace-карток (вода, потік енергії) |
| `board-config/systemd/`, `board-config/etc/` | юніти і системні файли плати; `new-board/` — те, що відрізняється на поточній платі |
| `board-config/custom-integrations/` | інтеграція `claude_code_conversation` і патчі Smart Irrigation |
| `mcp-server/` | локальний read-only MCP-сервер `home-assistant-project` і його тести |
| `tools/` | допоміжні скрипти для робочої станції (статистика, перевірка посилань дашборда) |
| `docs/`, `handoff/` | проєктні документи, `worklog.md` — журнал робіт (знахідки, рішення власника, коміти), реєстр інцидентів, передачі сесій |
| `.claude/skills/` | скіли `home-assistant`, `dashboard-design`, `mb35x8-bench` з довідниками |
| `nas-materials/` | матеріали з NAS: схема MB35x8 v1.1, BOM, Gerber, документація Rockchip |
| `mb35x8-software/` | аналіз резервної копії ПЗ плати |

**Секретів тут немає.** Тека `.storage/` (де Home Assistant тримає токени, ключі
Tuya та облікові дані), база даних і логи свідомо не включені.

## Пристрої Tuya — два канали одночасно

| | Tuya (хмара) | LocalTuya (локально) |
|---|---|---|
| Шлях | пристрій → хмара Tuya → HA | пристрій → локальна мережа → HA |
| Інтервал оновлення, **заміряно** | 216 с у середньому, до 1445 с | **24.5 с** для попередніх пристроїв; T34 насоса опитується кожну 1 с |
| Працює без інтернету | ні | **так** |

Обидві інтеграції працюють паралельно. Локальні сутності мають суфікс `_2` там, де
хмарна вже зайняла базовий `entity_id`. Для контролера автополиву локальні
клапани мають явні назви `switch.avtopoliv_kontroler_avtopoliv_klapan_1` … `_8`.

| Пристрій | IP | Локальних сутностей |
|---|---|---|
| Лічильник 3-фазний | `192.168.50.219` | 6 → 9 сенсорів |
| Зарядка 7.5 кВт | `192.168.50.36` | 28 |
| Автополив | `192.168.50.221` | 8 локальних клапанів |
| Насос свердловини T34 | `192.168.50.26` | 7, протокол 3.5, опитування 1 с |

Насос свердловини переведено на локальні сутності LocalTuya 21 серпня 2026.
Сторінка свердловини, ознака роботи насоса та власний інтегральний лічильник
використовують `sensor.t34_smart_plug_power_2`; хмарні сутності залишені як
контроль. Home Assistant записує в історію зміни стану, тому незмінні `0 W` не
створюють окремий рядок щосекунди навіть при опитуванні раз на секунду.

## Панель «Потужність»

`board-config/power_dashboard.yaml` — окрема панель у режимі YAML, доступна за
адресою `/power-dashboard/power`: стрілочний індикатор, графіки сирих станів,
`statistics-graph` з періодом `5minute`.

Вона існує тому, що **штатна панель «Енергія» принципово погодинна**. Та панель
показує **kWh** (спожиту енергію, накопичувальний підсумок) з довгострокової
статистики, і зробити її похвилинною неможливо. Для миттєвої потужності в **kW**
потрібні саме графіки сирих станів.

Основне джерело імпорту штатної панелі —
`sensor.inverter_total_energy_import`. Хмарний
`sensor.energy_meter_total_energy` не використовується як основний: при втраті
автентифікації Tuya він стає `unavailable` і залишає денний графік порожнім.
Налаштування джерела зберігається штатним UI/API Home Assistant, а його поточний
стан, денні показники й пояснення погодинної затримки видно на вкладці
«Потужність → Вибір періоду» в картці «Стан обліку Energy».

## Проєктні скіли та MCP-сервер

Операційні знання тепер зберігаються разом із конфігурацією Home Assistant:

- `.claude/skills/home-assistant/` — безпечне розгортання, діагностика, полив,
  енергія та інвентар мережі;
- `.claude/skills/mb35x8-bench/` — діагностика плати/ОС і правила прошивання;
- `.mcp.json` та `mcp-server/` — локальний read-only MCP-сервер
  `home-assistant-project`.

MCP-сервер показує стан плати (з переліком `problems`: файлова система,
бекапи, Tailscale, інвертор, насос, привиди в реєстрі), Git, останні журнали
HA, стани сутностей за регулярним виразом, журнал сповіщень, запускає
офіційний `check_config`, читає інвентар фіксованих пристроїв, перевіряє
LocalTuya-канали поливу та свердловинного насоса, баланс «мережа / Deye /
поза інвертором», порівнює SHA-256 файлів плати з `board-config/` і живий
конфіг storage-дашбордів із їхніми файлами. Він навмисно не вміє редагувати
live-файли, `.storage`, БД recorder, локальні ключі, реквізити або токени.

CLI-режим із кореня репозиторію:

```powershell
python mcp-server/cli.py git
python mcp-server/cli.py health
python mcp-server/cli.py sync
python mcp-server/cli.py dashboards
python mcp-server/cli.py incidents
python mcp-server/cli.py states "yasno|svitlo"
python mcp-server/cli.py notify-log
python mcp-server/cli.py irrigation-health
python mcp-server/cli.py well-pump-health
python mcp-server/cli.py energy-flow-health
python mcp-server/cli.py inventory Deye
python mcp-server/cli.py validate
```

Адміністрування через API Home Assistant (без `.storage`) робиться скриптами
на платі: `scripts/ha_admin.py` (привиди в реєстрі, одиниці статистики,
ресурси карток, панель сповіщень, Repairs) і `scripts/lovelace_push.py`
(storage-дашборди з YAML-файлів репозиторію). Обидва в `board-config/scripts/`.

Якщо Python MCP SDK ще відсутній:

```powershell
python -m pip install -r mcp-server/requirements.txt
```
