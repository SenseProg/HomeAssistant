# Матриця ролей Home Assistant

Складено 2026-08-10 за фактичним станом плати, не за бажаним.

## Що є зараз

| | |
|---|---|
| Облікових записів людей | **один** — «Дім Ковтуни», власник і адміністратор, без обмеження на локальну мережу |
| Осіб без облікового запису | Катерина, Олеся, Бабуся Сіма — існують лише як трекери присутності, увійти не можуть |
| Довгоживучих токенів | 2, обидва з правами власника |
| Дашбордів | Огляд, Енергія, Пристрої, Мапа — жоден не має `require_admin` |
| Сутностей, виставлених в Assist | **0** (тобто MCP-сервер HA, якщо його ввімкнути, не покаже нічого, поки список не поповнять) |
| Доступ ззовні | немає: ні Nabu Casa, ні DDNS, ні прокидання портів, ні VPN. Тільки локальна мережа, за IP |

Тобто ролей сьогодні фактично не існує: хто зайшов — той власник.

## Головне, що треба знати перед тим, як складати ролі

**Home Assistant не має прав на окремі сутності.** Це не налаштування, якого ми
не знайшли, — його немає в продукті. Реально розрізняються лише три групи:

| Група | Що справді забороняє |
|---|---|
| **Administrators** | нічого, повний доступ |
| **Users** | налаштування, інтеграції, користувачів, Developer Tools, дашборди з `require_admin`. **Але керувати можна будь-чим** — виклик служби через API не перевіряє, чи видно сутність на дашборді |
| **Read Only** | будь-яку зміну стану. Єдина група, про яку можна сказати «точно нічого не зламає» |

Звідси два наслідки, які визначають усю матрицю:

1. **Сховати вкладку — не те саме, що заборонити.** `require_admin` на дашборді
   і `visible:` на вкладці прибирають її з очей, але сутність лишається
   доступною через API будь-кому з групи Users. Для дитини чи гостя це не
   захист.
2. **Єдиний надійний рівень «дивитись, але не чіпати» — Read Only.** Проміжного
   «може вмикати світло, але не ворота» в HA немає.

Ще один важіль, який працює по-справжньому: **`local_only`** на обліковому
записі — такий користувач може увійти лише з локальної мережі. Оскільки доступу
ззовні тут немає навмисно, цей прапорець варто мати на всіх записах: він нічого
не змінює сьогодні і рятує, якщо колись щось випадково опиниться назовні.

## Матриця

| Роль | Механізм HA | Хто | Може | Не може |
|---|---|---|---|---|
| **Власник** | owner + Administrators, `local_only` | Дмитро | усе: інтеграції, користувачі, файли, токени | — |
| **Дорослий** | Users, `local_only` | Катерина | керувати всіма пристроями, дивитись історію й енергію | змінювати інтеграції та користувачів, Developer Tools, адмінські дашборди |
| **Дитина** | Users, `local_only`, обмежений набір вкладок | Олеся, хлопці | те саме, що дорослий, — з обмеженням лише візуальним | те саме, що дорослий |
| **Спостерігач** | **Read Only**, `local_only` | Бабуся Сіма, гості | бачити стан, температуру, камеру | будь-яке керування — це єдина роль, де заборона справжня |
| **Автоматика / API** | окремий запис у Users, `local_only`, під нього перевипустити токени | MCP-сервер, скрипти, зовнішні інтеграції | те, що виставлено в Assist | адмінські дії, вхід не з локальної мережі |

Рядок «Дитина» свідомо не обіцяє більше, ніж HA вміє: технічно він дорівнює
«Дорослому», відрізняється лише набором видимих вкладок. Якщо потрібна справжня
заборона — це Read Only, іншого варіанту немає.

## Що в цьому домі варто захищати найперше

Не всі сутності рівні. За наслідками помилкового натискання:

| Сутність | Чому саме вона |
|---|---|
| `cover.sonoff_10016e1b2d` і `cover.sonoff_1001338bf7` — ворота | єдині сутності, що відкривають доступ на ділянку фізично |
| `switch.avtopoliv_kontroler_avtopoliv_klapan_1..8` + насос | залишений клапан — це затоплення, а не перевитрата |
| `water_heater.144036023323246_water_heater` — бойлер | 2.2 кВт і бак гарячої води |
| `switch.zariadka_7_5kvt_switch` — зарядка авто | найбільший споживач у домі |
| `camera.cam1` | приватність, а не керування |

Мінімум, який має сенс: ворота і полив — тільки Власник і Дорослий; усе, що
нижче за роллю, — Read Only.

## Що зробити, щоб матриця стала правдою

Порядок важливий: спершу облікові записи, потім обмеження. Інакше єдиний
наявний запис втратить доступ до власних дашбордів.

1. **Створити облікові записи** — Налаштування → Люди → додати людину, увімкнути
   «Дозволити входити в систему». Пароль задає користувач; асистент паролів не
   вводить. Прив'язати до вже наявних осіб (Катерина, Олеся, Бабуся Сіма), щоб
   присутність і обліковий запис були однією людиною, а не двома.
2. **Зняти галочку «Адміністратор»** з усіх, крім власника, і поставити
   «Тільки локальний доступ» **усім**, включно з власником.
3. **Бабусі й гостям — група Read Only.** У UI це окремий перемикач
   «Тільки перегляд» у картці користувача.
4. **Окремий запис для токенів.** Обидва наявні довгоживучі токени випущені від
   власника, тобто витік будь-якого з них дорівнює повному доступу. Створити
   службовий запис (Users + local_only), перевипустити токени від нього, старі
   відкликати в профілі власника.
5. **`require_admin: true`** на дашбордах, які нікому, крім адміністратора, не
   потрібні. Робити це **після** кроку 1, інакше вкладки зникнуть у єдиного
   наявного користувача.
6. **Перед увімкненням MCP-сервера HA** переглянути, що виставлено в Assist:
   зараз нуль, і саме цей список стане тим, чим MCP зможе керувати.

Кроки 1-4 потребують введення пароля, тому вони за користувачем. Кроки 5-6 —
конфігурація, їх можна зробити скриптом, коли записи існуватимуть.
